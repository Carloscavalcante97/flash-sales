# Spec: F01 — sale with stock + purchase with atomic reservation

## Open Questions
None.

## Decisions
None.

## Goal
Add a `Sale` resource with an available-unit counter and an endpoint that
reserves exactly 1 unit per order. Under hundreds of concurrent purchase
requests the API must never reserve more units than the stock: N simultaneous
orders against stock E produce exactly min(N, E) `201`s and the rest `409
SOLD_OUT`. Postgres via the existing `PrismaService`. No Redis.

## Function / API signatures

### Prisma schema (append to `apps/api/prisma/schema.prisma`)
```prisma
model Sale {
  id     String  @id @default(uuid())
  name   String
  stock  Int     // units still available; decremented by each reservation
  orders Order[]

  @@map("sales")
}

enum OrderStatus {
  RESERVED
}

model Order {
  id      String      @id @default(uuid())
  saleId  String
  buyerId String
  status  OrderStatus @default(RESERVED)
  sale    Sale        @relation(fields: [saleId], references: [id])

  @@map("orders")
}
```
- `id` is `String` (Postgres `text`), **not** `@db.Uuid`. Any string in `:id` must yield a clean 404. A `uuid` column would raise a cast error, and therefore a 500, on ids like `abc`.
- `Sale` has exactly 3 scalar fields, so the Prisma record *is* the response `{ id, name, stock }`. Do not add `createdAt` or `updatedAt` (see Out of scope).

### `apps/api/src/sales.service.ts`
```ts
import { randomUUID } from 'node:crypto';
import { ConflictException, Injectable, NotFoundException } from '@nestjs/common';
import { PrismaService } from './prisma.js';

@Injectable()
export class SalesService {
  constructor(private readonly prisma: PrismaService) {}

  // prisma.sale.create({ data: { name, stock } }); returns the record as-is
  create(name: string, stock: number): Promise<{ id: string; name: string; stock: number }>;

  // prisma.sale.findUnique({ where: { id } }); null -> throw new NotFoundException()
  findOne(id: string): Promise<{ id: string; name: string; stock: number }>;

  reserve(saleId: string, buyerId: string): Promise<{ orderId: string; status: 'RESERVED' }>;
}
```

`reserve` must be implemented as **one SQL statement** run through Prisma's
tagged-template `$executeRaw`, exactly like this:
```ts
async reserve(saleId: string, buyerId: string) {
  const orderId = randomUUID();
  // ponytail: one statement = decrement + insert are atomic with no interactive transaction.
  // Under concurrency Postgres waits on the row lock and re-checks `stock > 0`
  // on the new row version, so stock can never go below 0.
  const inserted = await this.prisma.$executeRaw`
    WITH reserved AS (
      UPDATE sales SET stock = stock - 1
      WHERE id = ${saleId} AND stock > 0
      RETURNING id
    )
    INSERT INTO orders (id, "saleId", "buyerId")
    SELECT ${orderId}, id, ${buyerId} FROM reserved`;
  if (inserted === 1) return { orderId, status: 'RESERVED' as const };
  await this.findOne(saleId); // throws 404 if the sale does not exist
  throw new ConflictException({ error: 'SOLD_OUT' });
}
```
Why this shape. It is deliberate, and the Simplifier must not "simplify" it into Prisma calls:
- A conditional `UPDATE ... WHERE stock > 0` is atomic under READ COMMITTED. A concurrent updater waits for the lock, then *"the WHERE clause is re-evaluated to see if the updated version of the row still matches"* (https://www.postgresql.org/docs/17/transaction-iso.html, section 13.2.1).
- The data-modifying CTE feeds the `UPDATE ... RETURNING` rows into the `INSERT`. If the UPDATE matches 0 rows, 0 orders are inserted. Both happen in one implicit transaction (https://www.postgresql.org/docs/17/queries-with.html, "Data-Modifying Statements in WITH").
- **Rejected alternatives:**
  - `updateMany` + `order.create` as two calls: a crash between them loses a unit.
  - `prisma.$transaction(async tx => ...)`: it holds a pooled connection across 4 round trips while every buyer queues on the same row lock. Under hundreds of concurrent requests that risks Prisma's `maxWait` (P2028), which surfaces as 500s.
  - `sale.update({ where: { id, stock: { gt: 0 } }, data: { orders: { create } } })`: a nested write, and Prisma may read the row before writing it.
- `$executeRaw` returns the number of affected rows, and tagged-template values are sent as prepared-statement parameters (https://www.prisma.io/docs/orm/prisma-client/using-raw-sql/raw-queries). **Never** use `$executeRawUnsafe`, `Prisma.raw`, or string concatenation.
- The `status` column is omitted from the INSERT on purpose. Its DB default `'RESERVED'` fills it, so no enum cast is needed.
- `ConflictException` with an object argument sends that object verbatim as the body. Verified in the installed `@nestjs/common@12.5.0` `HttpException.createBody`, which returns `arg0` when it is an object. The body is therefore exactly `{"error":"SOLD_OUT"}`.

### `apps/api/src/sales.controller.ts`
```ts
@Controller('sales')
export class SalesController {
  constructor(private readonly sales: SalesService) {}

  @Post()                 // 201 (Nest default for @Post)
  create(@Body() body: Record<string, unknown> | undefined);   // validate, then this.sales.create(name, stock)

  @Get(':id')             // 200
  findOne(@Param('id') id: string);                            // this.sales.findOne(id)

  @Post(':id/orders')     // 201
  order(@Param('id') id: string, @Body() body: Record<string, unknown> | undefined); // validate, then this.sales.reserve(id, buyerId)
}
```
Validation is inline in the handlers. It is a few lines, because no validation
library is installed (`class-validator` and `zod` are both absent from
`apps/api/package.json`) and none may be added. Read the fields via
`body?.field`, because `body` can be `undefined` when no JSON body is sent.
Throw `new BadRequestException('<message>')` when a check fails:
- `name`: `typeof name === 'string' && name.trim() !== ''`. Store it as received, without trimming.
- `stock`: `typeof stock === 'number' && Number.isInteger(stock) && stock >= 1 && stock <= 2_147_483_647`. The upper bound is Postgres `INTEGER` max, and a larger value would otherwise become a Prisma 500.
- `buyerId`: `typeof buyerId === 'string' && buyerId.trim() !== ''`.
- Unknown extra body fields are ignored: not stored and not echoed.
- Body validation runs **before** any DB access. A request that is both invalid and aimed at a nonexistent sale returns 400.

### Routes (contract, verbatim from the request)
| Route | Body | Success | Errors |
|---|---|---|---|
| `POST /sales` | `{ "name": string, "stock": int > 0 }` | `201 { id, name, stock }` | `400` invalid payload |
| `GET /sales/:id` | none | `200 { id, name, stock }`, where stock = units available | `404` |
| `POST /sales/:id/orders` | `{ "buyerId": string }` | `201 { orderId, status: "RESERVED" }` | `409 { "error": "SOLD_OUT" }` · `404` unknown sale · `400` missing/invalid `buyerId` |

## Acceptance criteria
All are checked over HTTP with supertest against an app built from `AppModule`,
following the pattern in `apps/api/test/app.e2e-spec.ts`, plus `PrismaService`
for DB assertions.
1. `POST /sales` with `{"name":"Tênis","stock":10}` returns 201, and the body deep-equals `{ id: <non-empty string>, name: "Tênis", stock: 10 }` with no other keys.
2. `GET /sales/:id` with the id from (1) returns 200, and the body deep-equals `{ id, name: "Tênis", stock: 10 }`.
3. `GET /sales/does-not-exist` returns 404. `GET /sales/<random UUID>` returns 404. Neither returns 500.
4. `POST /sales` returns 400 for each of these bodies:
   - `{"name":"x"}` (stock missing)
   - `{"name":"x","stock":0}`
   - `{"name":"x","stock":-1}`
   - `{"name":"x","stock":1.5}`
   - `{"name":"x","stock":"5"}`
   - `{"name":"x","stock":null}`
   - `{"name":"x","stock":2147483648}`
   - `{"stock":5}` (name missing)
   - `{"name":"","stock":5}`
   - `{"name":"   ","stock":5}`
   - `{"name":123,"stock":5}`
   - an empty request with no body
   
   After all of them, no new row exists in `sales`.
5. `POST /sales` with `{"name":"x","stock":2147483647}` returns 201 with `stock: 2147483647`.
6. `POST /sales` with `{"name":"x","stock":3,"id":"forced","extra":1}` returns 201. The returned `id` is not `"forced"`, and the body has no `extra` key.
7. Against a sale with stock 2, `POST /sales/:id/orders` with `{"buyerId":"b1"}` returns 201. The body deep-equals `{ orderId: <non-empty string>, status: "RESERVED" }`. A following `GET /sales/:id` returns `stock: 1`.
8. After (7), the `orders` table has exactly one row with `id = orderId`, `saleId = <sale id>`, `buyerId = "b1"` and `status = "RESERVED"`.
9. Against a sale with stock 1: the first order returns 201. The second returns 409 with a body that deep-equals `{ "error": "SOLD_OUT" }`. `GET` then returns `stock: 0`, and the sale has exactly 1 order row.
10. Repeated orders on a sold-out sale keep returning 409. `stock` stays `0` and never goes negative, and no new order rows appear.
11. `POST /sales/does-not-exist/orders` with `{"buyerId":"b1"}` returns 404, and no order row is created.
12. `POST /sales/:id/orders` on an existing sale with stock returns 400 for each of these bodies: `{}`, `{"buyerId":""}`, `{"buyerId":"   "}`, `{"buyerId":123}`, `{"buyerId":null}`, and an empty request with no body. `stock` is unchanged afterwards.
13. `POST /sales/does-not-exist/orders` with `{}` returns 400, because validation runs before the lookup.
14. **Concurrency:** create a sale with stock 50, fire 200 `POST /sales/:id/orders` concurrently (`Promise.all`, distinct `buyerId`s). Exactly 50 responses are 201 and exactly 150 are 409 with body `{ "error": "SOLD_OUT" }`. None is 500 or anything else. The 50 `orderId`s are distinct. `GET` returns `stock: 0`. The DB has exactly 50 orders for that sale.
15. **Concurrency, stock 1:** create a sale with stock 1 and fire 100 concurrent orders. Exactly 1 returns 201, 99 return 409, and the final stock is 0.
16. **Concurrency across sales:** fire concurrent orders against sale A (stock 5) and sale B (stock 5), 30 to each, interleaved. Each sale ends up with exactly 5 orders and `stock: 0`.
17. The same `buyerId` can reserve repeatedly while stock lasts. Against a sale with stock 2, two orders with `buyerId:"same"` both return 201, and the third returns 409. There is no per-buyer limit.
18. **SQL injection:** `POST /sales/:id/orders` with `{"buyerId":"x'); DROP TABLE orders; --"}` returns 201. The stored `buyerId` equals that exact string, and the `orders` table still exists.
19. The existing `GET /` → `Hello World!` e2e test still passes. `pnpm --filter api typecheck`, `pnpm --filter api lint` and `pnpm --filter api test` pass.

## Edge cases to cover
- Wrong types for `stock`: string `"5"`, float, `0`, negative, `null`, boolean, above int4 max → 400.
- `name` and `buyerId` that are empty, whitespace-only, non-string or `null` → 400.
- No body, or a non-object JSON body such as `[]` → 400. Malformed JSON is already rejected with 400 by Nest's built-in body parser, so do not add handling for it.
- Arbitrary non-UUID strings as `:id` → 404, never 500.
- A sold-out sale: 409 with the exact body, stock stays exactly 0, no orphan order row.
- An unknown sale on the order route: 404 with no side effects.
- An invalid body plus an unknown sale → 400, because validation runs first.
- Bursts of concurrent orders (N > E), including E = 1, and concurrent bursts on two different sales.
- Repeat orders by the same buyer are allowed.
- Extra fields in `POST /sales` cannot override `id` or `stock` handling and are not echoed.
- E2E prerequisites (Tester): `docker compose up -d postgres` plus `pnpm --filter api exec prisma migrate deploy` before `pnpm --filter api test:e2e`. Each test creates its own sale, so no DB cleanup is needed. supertest 7.3.2 handles concurrent requests on a non-listening `app.getHttpServer()` through its shared-start logic, so `app.init()` is enough.

## Security
- **Who may call:** anyone, because authentication is explicitly out of scope for F01. The backend-nest Firebase guard must **not** be added. This is an accepted, known gap.
- **Input validation:** at the controller, per the rules above, before any DB access (criteria 4, 12, 13). Only `name`, `stock` and `buyerId` are read from bodies, and all other fields are ignored (criterion 6).
- **SQL injection:** the only raw SQL is the `$executeRaw` tagged template, and every value is a bound parameter. `$executeRawUnsafe`, `Prisma.raw` and string-built SQL are forbidden (criterion 18).
- **Data leaving the system:** `Sale` gives `{id, name, stock}`. An order gives `{orderId, status}`, and `buyerId` is never echoed. Error bodies are Nest defaults or exactly `{error:"SOLD_OUT"}`. Prisma/pg error details must not reach clients, which Nest's default 500 handler already guarantees, so do not add a filter.
- **Integrity invariant:** stock never goes below 0 and orders never exceed the initial stock (criteria 9, 10, 14–16).
- **Size limits:** Express's default 100 kB JSON limit caps `name` and `buyerId`. No extra limit is needed.
- **Secrets/config:** none new. `DATABASE_URL` keeps working as it does today.
- **Rate limiting:** none in F01.
- **Logging:** add none. Never log `buyerId` or request bodies.

## Fix Plan (iteration 1)
### Root cause
Postgres `text` (UTF8) cannot hold U+0000. The pg driver sends every JS string as a bound UTF-8 parameter, and Postgres rejects the 0x00 byte with SQLSTATE `22021` before the query runs, so Nest turns it into a 500. The spec's guarantees ("Any string in `:id` must yield a clean 404", and the `name`/`buyerId` rules) assumed every JS string is a valid `text` value. NUL is the one exception. Three user strings reach a text parameter unchecked:
- `:id` in `apps/api/src/sales.service.ts:14` (`findOne` → `prisma.sale.findUnique`) and in `sales.service.ts:24` (`reserve` → `$executeRaw`). This is **failure 1, a bug**: it breaks the spec lines quoted above.
- `name` (`sales.controller.ts:13` → `prisma.sale.create`) and `buyerId` (`sales.controller.ts:30` → `$executeRaw`). This is **failure 2, a spec gap**: these strings pass the spec's validation rule.

Sale ids are always generated (`@default(uuid())`) and never contain NUL. So an id containing NUL cannot match a sale, and the correct answer is a 404 without a DB round trip. Catching Prisma/pg error codes after the fact is rejected: the code differs between `findUnique` and `$executeRaw`, and a catch would also hide real DB failures.

**Spec gap disposition (failure 2): recommend it becomes a requirement, answered with 400.** The alternative of stripping or replacing NUL contradicts the existing rule "Store it as received, without trimming". A string the DB cannot store as received is an invalid payload, which the contract already answers with `400`. If the human gate rejects the requirement, skip the controller edit below and delete breaker tests 2a and 2b. NUL in `name`/`buyerId` then stays a known 500. Stock integrity holds either way, because the failed statement rolls back as a whole.

Acceptance criteria for this fix:
- F1. `GET /sales/%00` returns 404. `POST /sales/%00/orders` with `{"buyerId":"b1"}` returns 404 and creates no order row.
- F2. `POST /sales/%00/orders` with `{}` returns 400, because validation still runs before the lookup.
- F3. (Only if the gap is accepted.) `POST /sales` with `{"name":"a\u0000b","stock":1}` returns 400, and no new row exists in `sales`.
- F4. (Only if the gap is accepted.) `POST /sales/:id/orders` with `{"buyerId":"a\u0000b"}` on a sale with stock 1 returns 400. Stock stays 1 and no order row is written.
- All 19 original criteria still pass, along with `typecheck`, `lint` and `test`.

## Fix Plan (iteration 2)
### Root cause
The product is fine; the flakiness comes from how the tests are run. `apps/api/vitest.config.e2e.ts` keeps Vitest's default `fileParallelism: true`, so each `*.e2e-spec.ts` file runs in its own worker at the same time as the others, and all of them share one Postgres database. `apps/api/test/sales.e2e-spec.ts` checks criterion 4 by comparing a **global** count before and after the request: `const before = await prisma.sale.count()` and then `expect(await prisma.sale.count()).toBe(before)` (lines ~100–112). Criterion 11 and the order-route edge case do the same with `prisma.order.count()` (lines ~196–210). These checks only hold if nothing else writes to the database between the two counts. Iteration 1 added `test/sales.nul.e2e-spec.ts`, which creates sales and orders from a parallel worker, and that breaks the assumption. The Tester measured 7 of 19 failing runs with that file present and 0 of 15 without it, and the failure was always `expected N+1 to be N` after the `.expect(400)` had passed. Tests inside one file already run one after another (no `describe.concurrent`/`it.concurrent` is used; the `Promise.all` bursts in criteria 14–16 stay inside a single test), so running the files one at a time is enough to make every global count reliable again.

Acceptance criteria for this fix:
- F5. Running the whole e2e suite (`CI=true ./node_modules/.bin/vitest run --config ./vitest.config.e2e.ts` from `apps/api`, all 4 files) 15 times in a row exits 0 on every run, with 53/53 tests passing.
- F6. F1–F4 and all 19 original criteria still pass, along with `typecheck`, `lint`, `test` and `test:e2e`.

### Changes for the Coder
- `apps/api/vitest.config.e2e.ts`: inside the `test` object, add `fileParallelism: false, // ponytail: e2e files share one Postgres DB and assert global row counts, so run files one at a time (whole suite ~2s); per-file schemas if it gets slow`. Change nothing else in the file. Per https://vitest.dev/config/fileparallelism (default `true`), "Setting this to `false` will override `maxWorkers` option to `1`". The option exists in the installed vitest 4.1.12 (`fileParallelism?: boolean` in its config types), and the repo already uses the CLI form in the `test:debug` script (`--no-file-parallelism`).
