# F05: saga de pagamento com compensação

## Contrato da API

**Esta feature muda o contrato de `POST /orders/:id/pay` da F03**: o pagamento
passa a ser assíncrono, por um gateway falso. As outras rotas não mudam.

- `POST /orders/:id/pay { "paymentToken": string }`. O token tem de 1 a 255
  caracteres ASCII visíveis (0x21 a 0x7E); fora disso, ou sem corpo → `400`.
  - pedido `RESERVED` antes do `expiresAt` → passa a `PAYMENT_PENDING` e
    responde `202 { "orderId", "status": "PAYMENT_PENDING" }`;
  - pedido já `PAYMENT_PENDING` → `202` com o mesmo corpo, sem cobrar de novo
    (o token novo é ignorado);
  - pedido `PAID` → `200 { "orderId", "status": "PAID" }`;
  - pedido `CANCELLED` → `409 { "error": "PAYMENT_DECLINED" }`;
  - pedido `EXPIRED`, ou `RESERVED` com `expiresAt` já passado →
    `409 { "error": "RESERVATION_EXPIRED" }`;
  - pedido inexistente → `404`.
- `GET /orders/:id` passa a devolver também `"charges"`, o número de cobranças
  aprovadas desse pedido, e `status` ganha `"PAYMENT_PENDING"` e `"CANCELLED"`.

**Gateway falso.** Módulo interno e determinístico pelo token: token que começa
com `tok_decline` é recusado; qualquer outro é aprovado.

**Saga.** Os passos andam por mensagens no RabbitMQ, todas publicadas pelo
outbox da F04 na exchange `flash-sales.events`, com o mesmo formato de mensagem:

1. `POST /pay` grava `PAYMENT_PENDING` e o evento `payment.requested`
   (o corpo inclui também `paymentToken`).
2. O worker de pagamento, `node dist/payment-worker.js` (entrada
   `apps/api/src/payment-worker.ts`), consome `payment.requested`, chama o
   gateway e grava `payment.approved` ou `payment.declined`.
3. Aprovado → pedido `PAID` e evento `order.paid`.
   Recusado → **compensação**: pedido `CANCELLED`, 1 unidade de volta ao
   estoque e evento `order.cancelled`.

## Regras

- Com API, relay e worker no ar, o pedido sai de `PAYMENT_PENDING` para `PAID`
  ou `CANCELLED` em até 5 s.
- Um pedido nunca termina `PAID` e `CANCELLED` ao mesmo tempo, e a compensação
  devolve a unidade exatamente uma vez.
- `charges` nunca passa de 1, mesmo com `payment.requested` entregue mais de uma
  vez ou com `POST /pay` repetido ou simultâneo.
- Um pedido `PAYMENT_PENDING` não expira. O TTL da F03 só vale para `RESERVED`.
- A invariante da F03 passa a ser
  `estoque + RESERVED + PAYMENT_PENDING + PAID = estoque inicial`.
- `:id` com byte NUL, que não seja UUID ou que não exista → `404`, nunca `500`.

## Fora do escopo

Retry de falha do gateway e DLQ (F07), estorno de pedido `PAID`, autenticação.
