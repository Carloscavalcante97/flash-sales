# F04: outbox transacional + RabbitMQ

## Contrato

As rotas HTTP da F01–F03 não mudam.

**Broker.** RabbitMQ do `docker-compose.yml`, em `RABBITMQ_URL` (padrão
`amqp://flash:flash@localhost:55672`). Cliente AMQP: `amqplib`.

**Exchange.** `flash-sales.events`, tipo `topic`, `durable: true`. Quem publica
declara a exchange ao subir.

**Eventos.** Cada mudança de estado de pedido publica um evento com routing key
igual ao `type`:

| type | quando |
|---|---|
| `order.reserved` | pedido criado (`201` em `POST /sales/:id/orders`) |
| `order.paid` | pedido passa a `PAID` |
| `order.expired` | pedido passa a `EXPIRED` |

Mensagem: corpo JSON
`{ "eventId", "type", "orderId", "saleId", "buyerId", "occurredAt" }`
(`eventId` UUID, `occurredAt` ISO-8601 UTC), `contentType: "application/json"`,
`persistent: true` e propriedade AMQP `messageId` igual ao `eventId`.

**Processos.**
- API: `node dist/main.js` (em `apps/api`, depois de `pnpm --filter api build`).
- Relay: `node dist/relay.js` (entrada `apps/api/src/relay.ts`). É o único
  processo que publica no RabbitMQ.

## Regras

- **Outbox.** O evento é gravado no Postgres na mesma transação da mudança de
  estado. Mudança confirmada sempre acaba publicada; mudança desfeita nunca é
  publicada.
- **Nenhum evento se perde.** O relay pode ser morto com `SIGKILL` a qualquer
  momento. Depois que ele volta, todo evento confirmado é publicado.
- **Entrega pelo menos uma vez.** O mesmo evento pode sair mais de uma vez, mas
  sempre com o mesmo `eventId`. Existe exatamente um `eventId` por
  `(orderId, type)`.
- **Latência.** Com o relay e o RabbitMQ no ar, o evento é publicado em até 2 s
  depois do commit.
- **A API não depende do broker.** Com o relay parado ou o RabbitMQ fora do ar,
  as rotas HTTP continuam respondendo como antes (`201`, `409`, …).
- Sem garantia de ordem entre eventos.

## Fora do escopo

Consumidores dos eventos, retry e DLQ (F07), limpeza de eventos antigos já
publicados e autenticação.
