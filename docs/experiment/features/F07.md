# F07: retry com backoff + DLQ no pagamento

## Contrato

Vale para o worker de pagamento da F05, que consome `payment.requested`.

**Gateway falso, novos comportamentos:**
- token `tok_flaky_<n>` (n de 1 a 9): as `n` primeiras tentativas de cobrança
  desse pedido falham com erro transitório; a seguinte é aprovada;
- `tok_decline*`: recusa de negócio, como na F05. Não é erro e não tem retry;
- modo do gateway, guardado no Postgres para valer em todos os processos:
  `PUT /admin/gateway { "mode": "up" | "down" }` → `200 { "mode" }` (outro
  valor → `400`) e `GET /admin/gateway` → `200 { "mode" }`. Com `down`, toda
  tentativa falha com erro transitório. Padrão: `up`.

**Retry.** Cada mensagem tem até `PAYMENT_MAX_ATTEMPTS` tentativas (padrão `5`),
com backoff exponencial que começa em `PAYMENT_RETRY_BASE_MS` (padrão `200`) e
dobra a cada tentativa.

**DLQ.** Quando a última tentativa falha, a mensagem vai para a fila durável
`payment.requested.dlq` e o pedido continua `PAYMENT_PENDING`.

- `GET /admin/dlq` → `200 { "count", "messages": [ { "eventId", "orderId", "attempts", "lastError" } ] }`.
- `POST /admin/dlq/reprocess` → `202 { "requeued": n }`. Devolve todas as
  mensagens da DLQ ao processamento, com o contador de tentativas zerado.
- `GET /orders/:id` passa a devolver também `"paymentAttempts"`, o número de
  tentativas de cobrança feitas para o pedido.

## Regras

- Falha transitória se resolve com retry: `tok_flaky_2` termina `PAID` com
  `paymentAttempts` = 3 e `charges` = 1.
- Falha que persiste vai para a DLQ: com o gateway `down`, a mensagem chega à
  DLQ depois de exatamente `PAYMENT_MAX_ATTEMPTS` tentativas.
- O reprocessamento funciona: com o gateway de volta a `up`,
  `POST /admin/dlq/reprocess` leva esses pedidos a `PAID` em até 5 s.
- Nenhuma mensagem se perde: se o worker morrer durante o backoff, a tentativa
  continua depois que ele volta. Para isso, o retry tem de passar pelo broker,
  não por um timer em memória.
- `charges` nunca passa de 1, com retry, reprocessamento ou mensagem duplicada.
- `PAYMENT_MAX_ATTEMPTS` e `PAYMENT_RETRY_BASE_MS` são lidas pelo worker ao
  subir.

## Fora do escopo

Autenticação das rotas `/admin` (ficam abertas neste projeto de estudo), alerta
de DLQ e reprocessamento seletivo.
